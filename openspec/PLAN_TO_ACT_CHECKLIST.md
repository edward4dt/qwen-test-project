# Plan → Act 就緒檢查清單

適用時機：每次在 Cline 的 Plan Mode 討論完一個任務，準備切到 Act Mode 動手實作之前。

## 六項檢查標準

| # | 檢查項目 | 通過標準 |
|---|---------|---------|
| 1 | Scenario 化 | 能寫成 `WHEN ... THEN ...` 的具體情境，不是只有一句話描述 |
| 2 | 依賴關係明確 | 所有依賴用任務編號列出（例如「依賴 A7」），不能用「之後」「應該」等模糊字眼 |
| 3 | 語言事實 vs 邏輯決策分離 | 涉及具體語言學規則宣稱的內容，一律視為**未查證**，需列進 fixtures 待辦，不可直接當作規劃結論；純邏輯/架構決策才能算數 |
| 4 | 完成標準可驗證 | 能用一句可檢驗的話講出「做完等於什麼狀態」 |
| 5 | 影響範圍已鎖定 | 確認這個改動沒有牽連到其他還沒排進任何 tasks.md 的模組；有牽連的話，先補一筆任務記錄，不能規劃到一半發現牽連就直接動手 |
| 6 | 時間上限 | Plan 討論超過 15-20 分鐘還無法通過上述 1-5 項，代表任務範圍太大或太模糊，應拆出一個更小的 spike 任務先驗證，而不是繼續討論 |

## 切 Act 前的提示詞模板

複製貼上到 Plan Mode 對話框最後一輪：

```
在切到 Act 之前，請依照以下六項自我檢查，逐項回答「通過」或「未通過」，未通過的項目要說明原因：

1. 這個任務能寫成 WHEN/THEN 的 Scenario 嗎？
2. 所有依賴的任務編號都列出來了嗎？
3. 這裡面有沒有牽涉到你不確定、需要外部查證的語言事實？如果有，列出來，
   不要當作已確認的規劃內容，改成待辦查證項目。
4. 完成標準是什麼？請用一句可驗證的話講出來。
5. 這個改動會不會牽連到其他還沒排進 tasks.md 的地方？
6. 有沒有哪一項你自己也講不清楚？

六項都通過，才回覆「可以切到 Act Mode」；只要有一項未通過，說明原因並留在 Plan 模式繼續討論。
```

## 通過範例（以 multi-language-support 的 L011 為例）

**任務**：定義 `PronunciationRule` 介面（語言無關框架層）

| 檢查項 | 回答 |
|---|---|
| 1. Scenario | WHEN 呼叫端傳入辨識文字與目標文字 THEN `evaluate()` 回傳包含 passed/similarity/feedback 的物件，不管底層是哪個語言的實作 |
| 2. 依賴 | 無依賴，這是最底層的介面定義，可獨立進行 |
| 3. 語言事實 | 不涉及，這是純 TypeScript 介面設計，不含任何語言學規則宣稱 |
| 4. 完成標準 | `base.ts` 定義好 `PronunciationRule` 與 `EvaluationResult` 兩個型別，且 `ko.ts`（示範骨架）能正確 implement 這個介面並通過 TypeScript 編譯 |
| 5. 影響範圍 | 僅影響 `src/lib/pronunciation-engine/` 目錄，後續 ja.ts/en.ts/id.ts 都要 import 這份介面，但這是預期內、已記錄在 design.md 的依賴，不是新發現的牽連 |
| 6. 時間 | 討論 5 分鐘內就能確認以上，未超時 |

→ 六項全過，可以切 Act。

## 未通過範例（以 L012 為例，示範第 3 項攔下的情況）

**任務**：把韓文收尾音規則搬進 `ko.ts`

| 檢查項 | 回答 |
|---|---|
| 1. Scenario | WHEN 輸入「꽃」 THEN 應輸出標準發音「꼳」（但這個具體對應關係本身就是語言事實，見第 3 項） |
| 2. 依賴 | 依賴 L011（介面已定義）、依賴 B6.5 spike 結果 |
| 3. 語言事實 | **未通過**——「收尾音變化規則」是具體語言學宣稱，不能因為模型講得有條理就當作規劃結論。必須先攔下來，轉成 fixtures 待查證項目（`__fixtures__/ko-receiving-tail.json`），查證來源確認後才能回頭把這項標記為通過 |
| 4. 完成標準 | 待第 3 項解決後才能定義 |
| 5. 影響範圍 | 僅限 `ko.ts`，不影響其他語言 plugin |
| 6. 時間 | 在 5 分鐘內就發現第 3 項卡住，及時攔下，不需要再往下聊 |

→ 第 3 項未通過，**不可切 Act**。正確下一步：先去查證 fixtures 內容（維基百科音韻學條目、教材、母語者確認），查證完成後才回來讓 Qwen 依照已驗證的 fixtures 寫規則邏輯，而不是讓它憑自己的訓練資料生一版你無法查證的規則。

## 與現有機制的關係
- 第 3 項攔下的項目 → 進 `RISK_LOG.md`（未驗證）或 `__fixtures__/*.json`（待查證）
- 第 5 項發現的牽連 → 補進對應 change 的 `tasks.md`，必要時開新 change（就像這次的 `multi-language-support`）
- 第 6 項觸發的 spike → 比照 `B6.5` 的模式，開一個獨立的驗證任務，命名沿用小數點插入慣例
